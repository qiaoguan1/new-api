# Feature Specification: 当前用户微信订单状态同步

**Feature Branch**: `codex/230-wechat-order-reconciliation`
**Created**: 2026-08-25
**Status**: In Progress
**Input**: 生产充值记录会将已被微信关闭的订单长期显示为待支付，只有逐个查单后聚合状态才更新。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 充值历史显示真实状态 (Priority: P1)

已登录用户打开充值记录时，可见的微信订单应显示当前可信状态，而不是长期停留在“待支付”。

**Why this priority**: 错误的待支付状态会让用户重复扫码、误判到账情况并降低支付可信度。

**Independent Test**: 使用一组当前用户的待支付、已关闭和已成功微信订单，读取当前用户充值列表，验证可见状态与微信查询结果和本地入账结果一致。

**Acceptance Scenarios**:

1. **Given** 当前用户的可见待支付微信订单已被微信关闭，**When** 查询充值列表，**Then** 该订单显示失败或关闭，不再显示待支付。
2. **Given** 当前用户的可见待支付微信订单已支付成功，**When** 查询充值列表，**Then** 只有通过既有完整订单校验并幂等入账后才显示已到账。

---

### User Story 2 - 列表刷新有界且可用 (Priority: P1)

用户读取充值历史时，即使微信接口缓慢或临时不可用，列表仍在明确上限内返回已有本地状态。

**Why this priority**: 支付上游故障不能拖垮账户中心或让充值历史整体不可用。

**Independent Test**: 构造超过上限的待支付订单和超时/错误查询，验证只处理有界数量、超过截止时间停止，并继续返回持久化列表。

**Acceptance Scenarios**:

1. **Given** 可见列表有超过五个待支付微信订单，**When** 同步状态，**Then** 单次最多查询五个。
2. **Given** 微信查询失败或超过统一截止时间，**When** 返回充值列表，**Then** 接口仍成功返回，不伪造成功或失败状态。

---

### User Story 3 - 用户与支付边界不变 (Priority: P1)

状态同步只处理当前登录用户自己的原生微信订单，其他用户和其他支付渠道不被查询或修改。

**Why this priority**: 充值和余额属于高风险边界，任何跨用户或跨渠道修改都不可接受。

**Independent Test**: 混合当前用户、其他用户、微信和非微信订单，验证仅当前用户待支付微信订单进入同步。

**Acceptance Scenarios**:

1. **Given** 列表含其他用户或非微信订单，**When** 状态同步，**Then** 这些订单不被查询或更新。
2. **Given** 重复 SUCCESS 查询或重复回调，**When** 入账处理，**Then** 余额最多增加一次。

### Edge Cases

- NOTPAY、USERPAYING 和未知状态不得标记已到账。
- CLOSED、REVOKED、PAYERROR 只允许从待支付转为失败。
- 本地已成功或已失败订单不得再次查询微信或改变状态。
- 配置无效、上游错误、上下文取消和数据库并发冲突都不得使列表接口整体失败。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 当前用户充值列表 MUST 仅同步可见的本用户待支付原生微信订单，且订单已超过原生二维码有效期。
- **FR-002**: 单次请求 MUST 最多查询五个订单，并共享一个不超过五秒的截止时间。
- **FR-003**: SUCCESS MUST 经过现有 appid、mchid、订单号、金额和币种校验后调用幂等入账。
- **FR-004**: CLOSED、REVOKED、PAYERROR MUST 将仍为待支付的本地订单更新为失败。
- **FR-005**: NOTPAY、USERPAYING 和未知状态 MUST 保持非到账状态。
- **FR-006**: 上游、配置、超时或单订单更新失败 MUST fail-open 到持久化状态，不得使列表请求失败。
- **FR-007**: 非微信、非待支付、其他用户和超过处理上限的订单 MUST 不发起微信查询。
- **FR-008**: 实现 MUST 保持 SQLite、MySQL 和 PostgreSQL 兼容，并复用现有事务与行锁入账路径。
- **FR-009**: 日志和响应 MUST 不新增凭据、微信敏感正文或跨用户订单数据暴露。
- **FR-010**: 无效商户订单号 MUST 在本地跳过，不得发送到微信；同步错误日志 MUST 只包含汇总计数和错误类别。

## Key Entities

- **可见充值订单**: 当前用户当前页中的充值订单及本地持久化状态。
- **微信订单结果**: 经过商户订单号查询得到的最小可信状态和已存在的完整交易字段。
- **同步预算**: 单次请求允许的最大查询数量和统一截止时间。

## Success Criteria *(mandatory)*

- **SC-001**: 已复现的三个陈旧待支付订单在一次或有界多次列表刷新后全部得到真实状态。
- **SC-002**: 单次列表读取微信查询数始终不超过五，最慢同步阶段不超过五秒。
- **SC-003**: 上游失败测试中列表成功返回率为 100%，错误到账次数为 0。
- **SC-004**: SUCCESS 重复处理下余额重复增加次数为 0。
- **SC-005**: 相关控制器、模型、跨数据库兼容、完整 Go 测试、审查和 CI 全部通过。

## Assumptions

- 当前生产微信商户配置和既有单订单查询/回调逻辑保持权威。
- 本功能只在当前用户充值列表返回前做有界最佳努力同步，不新增定时任务或客户端 N+1 查询。
- 生产部署与真实支付交易验证作为合并后的单独授权步骤处理。
